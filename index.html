    Pendahuluan

    Airpay Payment Gateway menyediakan Payin (menerima pembayaran dari pelanggan), Payout (mengirim dana ke tujuan), dan pembayaran berulang (recurring) di satu platform. Dokumen ini adalah referensi integrasi untuk merchant dan partner. Integrasi mengikuti standar SNAP (ASPI, Bank Indonesia) pada path /api/snap/v1.0.

    Baru mulai? Buka Quickstart. Sudah siap menguji? Jalankan skenario di UAT.

    Base URL dan lingkungan

    Semua contoh memakai placeholder {BASE_URL}. URL lengkap = {BASE_URL} + path, misalnya {BASE_URL}/api/snap/v1.0/emoney/topup.

    LingkunganBase URLCatatan
    Sandbox{BASE_URL_SANDBOX}Untuk pengembangan dan UAT. Kredensial terpisah dari produksi.
    Production{BASE_URL_PRODUCTION}Hanya setelah UAT selesai dan aktivasi disetujui.
    Alamat host dan kredensial per lingkungan diberikan tim integrasi saat onboarding. Client key, client secret, public key Airpay, dan base URL harus berasal dari lingkungan yang sama.

    Konvensi umum

    • Semua request memakai HTTPS dengan method POST dan body JSON (UTF-8).
    • Waktu memakai ISO-8601 dengan zona waktu, misalnya 2026-10-19T10:15:30+07:00.
    • Nama field camelCase; uang berupa objek {"value":"15000.00","currency":"IDR"} dengan value string dua desimal. Payout hanya IDR; payin menerima kode mata uang 3 huruf besar.
    • HTTP status selalu sama dengan 3 digit pertama responseCode.
    • Hasil akhir transaksi datang lewat notify dan tidak dikirim ulang. Selalu siapkan pengecekan status sebagai cadangan (lihat Notify).

    Quickstart

    Panduan singkat dari nol sampai transaksi pertama di sandbox. Hasil akhir tiap transaksi tetap harus diverifikasi lewat notify atau cek status.

    1. Siapkan client key, client secret, pasangan kunci RSA Anda (kirim public key ke tim integrasi), IP server untuk whitelist, dan notify_url.
    2. Buat X-SIGNATURE token: tanda tangan RSA-SHA256 atas clientKey|X-TIMESTAMP, lalu panggil access-token/b2b.
    3. Untuk setiap request transaksi, hitung X-SIGNATURE HMAC-SHA512 (contoh kode tersedia di 5 bahasa).
    4. Panggil 54 Debit Payment dengan partnerReferenceNo polos (tanpa awalan kode merchant) dan X-EXTERNAL-ID baru.
    5. Verifikasi notify bertanda tangan dari Airpay, atau cek hasilnya lewat 55 Debit Status.
    Jangan menambahkan awalan kode merchant pada partnerReferenceNo. Sistem kami menambahkannya sendiri, sehingga awalan dari Anda akan menjadi ganda (CFM-CFM-REF001).

    Autentikasi

    Autentikasi SNAP

    SNAP memakai dua lapis: (1) access token B2B yang diminta dengan tanda tangan asimetris RSA, lalu (2) setiap request transaksi ditandatangani simetris dengan HMAC-SHA512. Token berlaku 900 detik (default); setelah itu minta token baru.

    Dua pasang kunci dan satu secret

    Ada dua pasang kunci RSA yang berbeda arahnya, ditambah satu secret HMAC. Jangan tertukar.

    KunciPemilik private keyDi mana public key / secret disimpanDipakai untuk
    Pasangan kunci merchant (RSA)Anda. Private key tidak pernah Anda kirim ke kami.Public key Anda didaftarkan oleh tim integrasi pada data merchant Anda.Anda menandatangani X-SIGNATURE untuk access-token/b2b; kami memverifikasi dengan public key Anda.
    Client secret (HMAC-SHA512)Rahasia bersama Anda dan kami. Diberikan tim kami.Sama dengan client secret merchant Anda.Anda menandatangani setiap request transaksi (X-SIGNATURE HMAC); kami menghitung ulang dan membandingkan.
    Pasangan kunci AIRPAY (RSA)Kami (server Airpay). Private key hanya di server kami.Satu kunci untuk semua merchant (SNAP Notify Public Key). Tim integrasi menyerahkannya kepada Anda.Kami menandatangani setiap notify yang dikirim ke notify_url Anda; Anda memverifikasi dengan public key AIRPAY.
    Ringkas: tanda tangan access token = RSA dengan private key Anda; tanda tangan transaksi = HMAC dengan client secret Anda; tanda tangan notify = RSA dengan private key kami, diverifikasi dengan public key AIRPAY.

    Langkah

    1. Siapkan X-TIMESTAMP (waktu sekarang, format ISO-8601 dengan zona waktu).
    2. Susun string-to-sign: clientKey|X-TIMESTAMP (tanda pipa |, tanpa spasi).
    3. Tanda tangani dengan private key RSA Anda: SHA256withRSA (PKCS#1 v1.5), lalu encode Base64. Hasilnya = X-SIGNATURE.
    4. Panggil POST /api/snap/v1.0/access-token/b2b dengan header X-TIMESTAMP, X-CLIENT-KEY, X-SIGNATURE dan body {"grantType":"client_credentials"}.
    5. Simpan accessToken dari response; pakai sebagai Authorization: Bearer <accessToken> pada semua request transaksi selama expiresIn detik.

    Contoh string-to-sign

    clientKey      : sbox-airpay-8f14e45f-ceea-4f6a-9d3c-2b1a7c5e9d01
X-TIMESTAMP    : 2026-10-19T10:15:00+07:00
stringToSign   : sbox-airpay-8f14e45f-ceea-4f6a-9d3c-2b1a7c5e9d01|2026-10-19T10:15:00+07:00
X-SIGNATURE    : Base64( RSA-SHA256-PKCS1v15( privateKey, stringToSign ) )

    Contoh dengan openssl

    CLIENT_KEY="sbox-airpay-8f14e45f-ceea-4f6a-9d3c-2b1a7c5e9d01"
TS=$(date +"%Y-%m-%dT%H:%M:%S+07:00")
SIG=$(printf '%s|%s' "$CLIENT_KEY" "$TS" \
  | openssl dgst -sha256 -sign merchant_private.pem | openssl base64 -A)

curl -X POST '{BASE_URL}/api/snap/v1.0/access-token/b2b' \
  -H 'Content-Type: application/json' \
  -H "X-TIMESTAMP: $TS" \
  -H "X-CLIENT-KEY: $CLIENT_KEY" \
  -H "X-SIGNATURE: $SIG" \
  -d '{"grantType":"client_credentials"}'

    Signature transaksi (SNAP)

    Setiap request transaksi (bukan access token) ditandatangani dengan HMAC-SHA512 memakai client secret Anda. Server menghitung ulang signature dari request yang diterima; bila berbeda satu byte pun, ditolak 401<svc>00 Unauthorized. Signature.

    String-to-sign

    stringToSign = HTTPMethod + ":" + RelativePath + ":" + AccessToken + ":" + lowercase(hex(SHA256(minify(body)))) + ":" + X-TIMESTAMP

X-SIGNATURE  = Base64( HMAC-SHA512( clientSecret, stringToSign ) )
    • HTTPMethod: huruf besar, selalu POST.
    • RelativePath: path request apa adanya seperti diterima server, tanpa host, termasuk query string bila ada. Contoh: /api/snap/v1.0/emoney/topup. Bila Anda lewat reverse proxy yang mengubah path, tanda tangani path yang sampai ke server.
    • AccessToken: nilai token saja, tanpa kata Bearer.
    • minify(body): body JSON dipadatkan (tanpa spasi/baris baru di luar string). Kirim body dalam bentuk minify yang sama dengan yang Anda hash; urutan field tidak diubah. Body kosong dihash sebagai string kosong (e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855).
    • Hash = SHA-256 dari body minify, ditulis hex huruf kecil (64 karakter).
    • X-TIMESTAMP: nilai yang sama persis dengan header yang dikirim.

    Urutan pemeriksaan di server

    1. Header wajib (Authorization Bearer, X-TIMESTAMP, X-SIGNATURE, X-PARTNER-ID, X-EXTERNAL-ID, CHANNEL-ID) lengkap -> 400<svc>02.
    2. Format X-TIMESTAMP (dan dalam toleransi), X-PARTNER-ID (maks 36), X-EXTERNAL-ID (angka, maks 36), CHANNEL-ID (maks 5) -> 400<svc>01.
    3. Token valid -> 401<svc>01; X-PARTNER-ID sama dengan Partner ID pemilik token -> 401<svc>00 Unauthorized. Partner mismatch.
    4. IP dalam whitelist -> 401<svc>00 Unauthorized. IP not allowed.
    5. Signature HMAC cocok -> 401<svc>00 Unauthorized. Signature (body yang bukan JSON valid menjadi 400<svc>00 Bad Request).
    6. X-EXTERNAL-ID belum dipakai -> 409<svc>00 Conflict.

    Contoh kode: signature transaksi

    Setiap contoh di bawah menghasilkan nilai X-SIGNATURE yang sama persis dengan contoh perhitungan di atas (kGfJgiDc…7M4sQ==) untuk body, token, path, timestamp, dan secret yang sama.

    import base64, hashlib, hmac, json

def transaction_signature(client_secret, method, path, access_token, body_json, timestamp):
    """X-SIGNATURE untuk request transaksi SNAP (HMAC-SHA512)."""
    body_hash = hashlib.sha256(body_json.encode("utf-8")).hexdigest()  # hex huruf kecil
    string_to_sign = f"{method}:{path}:{access_token}:{body_hash}:{timestamp}"
    digest = hmac.new(client_secret.encode(), string_to_sign.encode(), hashlib.sha512).digest()
    return base64.b64encode(digest).decode()

    Contoh kode: verifikasi notify

    Gunakan raw body persis seperti diterima dan RelativePath(notify_url) yang sama dengan yang terdaftar. Setiap contoh menerima tanda tangan yang sah dan menolak body yang diubah satu karakter.

    import base64, hashlib
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.asymmetric import padding
from cryptography.exceptions import InvalidSignature

def verify_notify(airpay_public_key_pem, relative_path, raw_body, timestamp, signature_b64):
    """raw_body: byte persis yang diterima (jangan di-parse lalu serialisasi ulang)."""
    body_hash = hashlib.sha256(raw_body).hexdigest()
    string_to_sign = f"POST:{relative_path}:{body_hash}:{timestamp}".encode()
    key = serialization.load_pem_public_key(airpay_public_key_pem)
    try:
        key.verify(base64.b64decode(signature_b64), string_to_sign, padding.PKCS1v15(), hashes.SHA256())
        return True
    except InvalidSignature:
        return False
    const crypto = require("crypto");

// rawBody: Buffer/string persis seperti yang diterima (jangan di-parse lalu serialisasi ulang)
function verifyNotify(airpayPublicKeyPem, relativePath, rawBody, timestamp, signatureB64) {
  const bodyHash = crypto.createHash("sha256").update(rawBody).digest("hex");
  const stringToSign = `POST:${relativePath}:${bodyHash}:${timestamp}`;
  return crypto.createVerify("RSA-SHA256").update(stringToSign).verify(airpayPublicKeyPem, signatureB64, "base64");
}

    // publicKeyBase64 = isi PEM "PUBLIC KEY" (X.509 SPKI) tanpa header/footer dan baris baru
    // rawBody = byte persis seperti yang diterima
    static boolean verifyNotify(String publicKeyBase64, String relativePath, byte[] rawBody,
                                String timestamp, String signatureB64) throws Exception {
        byte[] h = MessageDigest.getInstance("SHA-256").digest(rawBody);
        StringBuilder hex = new StringBuilder();
        for (byte b : h) hex.append(String.format("%02x", b));
        String stringToSign = "POST:" + relativePath + ":" + hex + ":" + timestamp;
        PublicKey key = KeyFactory.getInstance("RSA")
            .generatePublic(new X509EncodedKeySpec(Base64.getDecoder().decode(publicKeyBase64)));
        Signature s = Signature.getInstance("SHA256withRSA");
        s.initVerify(key);
        s.update(stringToSign.getBytes(StandardCharsets.UTF_8));
        return s.verify(Base64.getDecoder().decode(signatureB64));
    }
}

    Idempotensi dan pengulangan request

    X-EXTERNAL-ID mencegah request ganda. Server mencatat pasangan (client key, tanggal, X-EXTERNAL-ID); request kedua dengan nilai sama pada hari yang sama dijawab 409<svc>00 Conflict.

    • Hanya angka, 1-36 karakter. Buat nilai baru untuk setiap request (mis. timestamp nano atau counter).
    • Keunikan berlaku per hari (zona waktu server, WIB) dan klaim disimpan 24 jam.
    • Bila request ditolak sebelum menyentuh partner (validasi, konfigurasi, partner tidak tersedia), klaim X-EXTERNAL-ID dilepas sehingga Anda boleh mengirim ulang dengan X-EXTERNAL-ID yang sama.
    • Bila request sudah sampai ke partner (termasuk hasil tidak pasti 500<svc>02 atau 504<svc>00), klaim tetap dipakai: kirim ulang harus dengan X-EXTERNAL-ID baru.
    • Terpisah dari itu, partnerReferenceNo (dan partnerRefundNo) harus unik per merchant; duplikat dijawab 409<svc>01 Duplicate partnerReferenceNo. Jangan membuat partnerReferenceNo baru untuk transaksi yang sama - cek status dulu (39 atau 55).
    • Bila hasil tidak pasti (timeout atau error 5xx), cek status lebih dulu (endpoint 55 atau 39) sebelum membuat transaksi baru.

    Keamanan dan perlindungan data

    Ringkasan praktik keamanan yang wajib dan dianjurkan untuk merchant. Rincian teknis tanda tangan ada di bagian Autentikasi dan Signature.

    Rahasia dan kredensial

    • Simpan client secret dan private key RSA hanya di server. Jangan menaruhnya di aplikasi mobile, JavaScript sisi klien, repositori kode, atau log.
    • Private key RSA Anda tidak pernah dikirim ke Airpay; hanya public key. Bila ada dugaan bocor, segera hubungi tim integrasi untuk mengganti kredensial.
    • Semua panggilan memakai HTTPS. Pastikan base URL, kredensial, dan public key Airpay berasal dari lingkungan yang sama.

    Menerima notify dan callback

    • SNAP: selalu verifikasi X-SIGNATURE dengan raw body dan public key Airpay, dan periksa X-TIMESTAMP masih wajar (mencegah replay). Tolak notify yang tidak lolos.
    • Endpoint penerima harus HTTPS, dapat dijangkau dari internet (bukan alamat privat), dan membalas dalam beberapa detik. Pada notify SNAP, redirect (3xx) tidak diikuti.

    IP whitelist (SNAP)

    SNAP hanya menerima request dari IP yang terdaftar. Daftar kosong berarti semua request ditolak. IP yang dinilai adalah IP asal koneksi (atau X-Real-IP dari proxy tepercaya kami); X-Forwarded-For tidak dipakai. Beri tahu tim integrasi setiap kali IP keluar server Anda berubah.

    Data kartu dan data pribadi

    • Field kartu (card_number, card_name, cvc, expired_date) hanya dipakai bila tim integrasi memintanya untuk metode kartu. Bila sistem Anda memproses data kartu, lingkungan Anda masuk lingkup PCI DSS.
    • Jangan mencatat nomor kartu, CVC, atau PIN di log. PCI DSS melarang menyimpan CVC/CVV setelah otorisasi. Gateway kami tidak menyimpan dan tidak mencatat pin payout.
    • Kirim data pelanggan (nama, email, telepon, alamat) hanya yang dibutuhkan channel. Seluruh data pada contoh di dokumen ini fiktif.

    Rate limit

    Batas request dihitung per client key per menit. Besar batas untuk setiap endpoint: lihat dashboard onboarding atau tanyakan tim integrasi {RATE_LIMIT_PER_ENDPOINT}.

    Notify

    Hasil akhir tidak dikirim ulang. Notify dikirim satu kali. Anda harus: (1) membalas HTTP 200 secepat mungkin, (2) memproses secara asinkron dan idempoten, dan (3) mengecek status sebagai cadangan bila tidak ada kabar. Mengirim ulang transaksi karena belum menerima notify dapat menimbulkan transaksi ganda.

    Hasil akhir transaksi dikirim server ke notify_url merchant sebagai HTTP POST JSON bertanda tangan. Berlaku untuk Payout Top Up (38) dan payin yang punya callback dari partner: pembayaran (54) dan refund (58). Endpoint 55 tidak menghasilkan notify.

    stringToSign = "POST" + ":" + RelativePath(notify_url) + ":" + lowercase(hex(SHA256(minify(rawBody)))) + ":" + X-TIMESTAMP

verify = RSA-SHA256-PKCS1v15-Verify( publicKeyAIRPAY, stringToSign, Base64decode(X-SIGNATURE) )
    • RelativePath(notify_url): path dari notify_url yang terdaftar pada data merchant Anda, termasuk query string bila ada. Contoh notify_url https://merchant.example/hook/snap?v=1 maka path = /hook/snap?v=1.
    • Tidak ada token di string-to-sign (berbeda dengan signature transaksi).
    • Hash dihitung dari body yang Anda terima: pakai raw body persis, lalu minify. Jangan parse lalu serialisasi ulang (urutan/escape bisa berubah).
    • Verifikasi juga X-TIMESTAMP masih wajar (mis. selisih beberapa menit) untuk mencegah replay.

    Respons yang kami harapkan dari Anda

    Balas HTTP 2xx. Dianjurkan body JSON format ASPI: {"responseCode":"2005600","responseMessage":"Successful"}. Balasan 2xx tanpa body, bukan JSON, atau tanpa responseCode tetap diterima. Bila body JSON memuat responseCode yang tidak diawali 200 (mis. 4005601), notify dicatat gagal beserta kodenya. Non-2xx, timeout, atau gagal koneksi juga dicatat gagal. Dikirim sekali, tanpa pengiriman ulang.

    Perilaku pengiriman

    • Notify dikirim satu kali per perubahan status yang diterima dari partner, secara asinkron setelah status transaksi tersimpan. Tidak pernah dikirim ulang, juga bila gagal (non-2xx, timeout, atau gagal koneksi): pengiriman ganda dapat dianggap transaksi kedua oleh sistem Anda.
    • Timeout pengiriman default 15 detik. Redirect (3xx) tidak diikuti. Tujuan alamat privat/loopback/link-local/CGNAT ditolak oleh sistem kami.
    • Bila notify tidak diterima, gunakan endpoint status untuk mengambil hasilnya: 39 (payout top up) atau 55 (payin pembayaran/refund).
    • Kami tidak mengirim ulang. Walau demikian, buat handler Anda idempoten (dedupe pada originalReferenceNo + latestTransactionStatus) sebagai pengaman bila partner mengirim callback berulang.
    • Bila signing key tidak tersedia di server kami, endpoint uang (38, 54, 58) menolak dengan 500<svc>00 General Error, sehingga tidak ada transaksi berjalan tanpa notify bertanda tangan.

    Kredensial dan konfigurasi

    • Client key, base URL, dan public key Airpay produksi sudah diterima dan berasal dari lingkungan yang sama.
    • Public key RSA Anda dan daftar IP keluar server produksi sudah didaftarkan. Daftar IP kosong menolak semua request.
    • notify_url sudah didaftarkan dan dapat dijangkau dari internet lewat HTTPS.
    • Kombinasi country/channel/service dan produk payout yang akan dipakai sudah dikonfirmasi aktif.

    Integrasi

    • Semua skenario di UAT lolos di sandbox.
    • partnerReferenceNo unik dan tidak pernah dipakai ulang, termasuk setelah gagal. X-EXTERNAL-ID unik per request.
    • Access token disimpan dan diperbarui sebelum kedaluwarsa (900 detik); respons 401 token ditangani dengan meminta token baru.
    • Handler notify membalas cepat, memproses asinkron, idempoten, dan memverifikasi signature dan timestamp.
    • Ada pengecekan status berkala untuk transaksi pending sebagai cadangan, dan rekonsiliasi harian. Notify hanya dikirim sekali.
    • Hasil tidak pasti (timeout, 5xx) tidak pernah memicu pengiriman ulang dengan partnerReferenceNo baru tanpa cek status.
    • Backoff dengan jitter dipasang untuk 429 dan error sementara.

    • Client secret dan private key hanya di server, tidak ada di log, repositori, atau aplikasi klien.
    • Tidak ada nomor kartu, CVC, atau PIN yang tercatat di log.

    • Kontak teknis dan eskalasi Anda sudah diserahkan ke tim integrasi, dan Anda tahu cara melapor (lihat Dukungan).
    • Alarm untuk lonjakan error, transaksi pending yang menua, dan notify yang gagal diproses.

    FAQ

    Di mana saya mendapat sandbox dan data uji?

    Tim integrasi menyerahkan base URL dan kredensial sandbox saat onboarding. Data uji ada di panduan sandbox {SANDBOX_TEST_DATA}. Skenario yang disarankan ada di UAT.

    Signature saya ditolak (Unauthorized. Signature). Apa yang dicek?

    Pastikan: method huruf besar; path persis (termasuk query bila ada); token tanpa kata Bearer; hash dari body minify dengan hex huruf kecil; X-TIMESTAMP sama dengan header; client secret benar; byte body yang dikirim sama dengan yang di-hash.

    Timestamp ditolak (Invalid Field Format X-TIMESTAMP).

    Gunakan format ISO-8601 dengan zona waktu (+07:00 atau Z) dan sinkronkan jam server Anda (NTP). Selisih maksimal dengan jam server default 5 menit.

    Kenapa 401 ... IP not allowed?

    IP server Anda belum ada di IP whitelist SNAP atau whitelist kosong. Beri tahu tim integrasi IP keluar server Anda.

    Berapa lama token berlaku?

    900 detik (default), lihat expiresIn. Minta token baru sebelum habis atau saat menerima Invalid Token (B2B).

    Dapat 409 Conflict.

    X-EXTERNAL-ID sudah dipakai hari ini. Pakai nilai baru. Bila 409 ... 01, itu partnerReferenceNo/partnerRefundNo duplikat.

    Dapat 504 atau 500xx02 saat Top Up/Pembayaran. Kirim ulang?

    Jangan buat partnerReferenceNo baru. Cek status (39 atau 55) dan tunggu notify. Mengirim ulang dengan referensi sama akan ditolak sebagai duplikat.

    Notify tidak sampai.

    Pastikan notify_url benar, dapat dijangkau dari internet (bukan alamat privat), dan membalas 2xx dalam beberapa detik. Notify dikirim satu kali dan tidak pernah dikirim ulang; gunakan 39/55 untuk mengambil hasilnya.

    Apakah notify dikirim ulang atau bisa datang dua kali?

    Kami tidak mengirim ulang (satu kali per perubahan status). Tetap buat handler idempoten dengan dedupe memakai originalReferenceNo + latestTransactionStatus.

    Perlu awalan Merchant Code pada partnerReferenceNo?

    Tidak. Kirim polos. Lihat bagian Standar ID.

    403 ... Feature Not Allowed [payout not enabled].

    Payout belum diaktifkan untuk merchant Anda. Hubungi tim integrasi.

    403 ... [channel not configured].

    Kombinasi country/channel/service tidak ada di konfigurasi merchant Anda. Periksa nilai atau minta tim integrasi menambahkannya.

    Apakah ada endpoint pembatalan, sandbox terpisah, atau batas rate limit tertentu?

    Tidak tercantum di dokumen ini. Hubungi tim integrasi.

    Dapat 504 atau 500xx02 saat Charge/Binding. Kirim ulang?

    Jangan buat partnerReferenceNo baru. Cek status (55 untuk charge, 08 untuk binding) dan tunggu notify. Mengirim ulang dengan referensi sama akan ditolak sebagai duplikat.

    Bagaimana mendapatkan hasil Binding (07)?

    Dari notify (serviceCode 07). Untuk mengecek status mandate kapan saja, pakai 08.
